# DBX Custom：DB2 10.1 / GB18030 只读验收

本分支基于 DBX 0.6.51，适用于 DB2 LUW 10.1.0.3（Fix Pack 3）到 TiDB 的比较排查。
源码测试、安装包构建、内网数据库验证是三个独立的验收结果。构建成功不代表业务库已经验证通过。

## 安装与组件核验

从个人仓库 Actions 中运行 **DBX Custom Windows**，选择 `main`，下载 `DBX-Custom-Windows-x64` 产物。
该工作流只上传构建产物，不创建 Release。安装包未使用官方代码签名证书。

1. 在 PowerShell 用 `Get-FileHash -Algorithm SHA256 -LiteralPath '安装包完整路径'` 核对随附 `.sha256`。
2. 安装 **DBX Custom**。它使用应用标识 `com.hunshui0.dbx.custom`，不继承官方连接配置。
3. 默认配置目录为 `%APPDATA%\com.hunshui0.dbx.custom`。测试前清除外部的 `DBX_DATA_DIR` 覆盖设置；不要将驱动目录改到官方 DBX 的目录。
4. 配置目录下的 `agents/drivers/db2/agent.jar` 摘要应与产物 `build-manifest.json` 的 `agentSha256` 相同。启动日志也记录源码提交和摘要。
5. Agent 使用随包的 Java 21，包含 `jdk.charsets`。保持驱动管理中的 Java 运行时为“托管”。不要设置 `-Ddb2.jcc.charsetDecoderEncoder=3`。
6. 官方应用自动更新和已固定 DB2 Agent 的在线更新均停用；更新此版本请使用新的自定义安装包。

本次只配置 `origin=https://github.com/hunshui0/dbx.git`。`master` 保存原版，`main` 保存修复。
今后从原库同步时，明确同步个人 `master`，再合并到 `main`；不要对自定义 `main` 执行覆盖式 fork 同步。

## 采集真实环境信息

截图中的 `db2level` 只证明实例版本，无法单独证明数据库代码页或每列的实际字节。
在 DB2 服务器现有连接中采集以下只读输出；不要执行建表、修复、导入或更新操作。

```text
db2level
db2 get db cfg for <数据库名>
```

保留配置输出中的 Database code page、Database code set、Database territory。
在 SQL 编辑器中执行，按实际 schema 替换 `ODS`：

```sql
SELECT CURRENT SERVER AS SERVER, CURRENT SCHEMA AS SCHEMA
FROM SYSIBM.SYSDUMMY1;

SELECT TABSCHEMA, TABNAME, COLNO, COLNAME, TYPENAME, LENGTH, CODEPAGE
FROM SYSCAT.COLUMNS
WHERE TABSCHEMA = 'ODS'
  AND TABNAME IN ('CUSTINFO','DEPSTS','FCKFH','FDKFH','FNBZFH','LONSTS')
ORDER BY TABSCHEMA, TABNAME, COLNO;
```

同时记录 DBX 构建清单、实际 JCC 版本、托管 Java 版本。内置 JCC 依赖保持原版本；本修复不盲目升级驱动。
GB18030 是用户提供的环境条件，诊断时仍以实际数据库及列代码页为准，尤其检查二进制字符列和混合导入的数据。

在 TiDB 中采集：

```sql
SELECT VERSION(), DATABASE();
SHOW VARIABLES LIKE 'character_set%';
SHOW VARIABLES LIKE 'collation%';
SHOW CREATE DATABASE `目标数据库`;
SHOW CREATE TABLE `目标数据库`.`CUSTINFO`;
SHOW CREATE TABLE `目标数据库`.`DEPSTS`;
```

## 分页和完整性验收

保持两端表在比较期间不发生变化；计数和分页读取不提供跨数据库一致性快照。

| 表 | 验收步骤 | 通过条件 |
| --- | --- | --- |
| FCKFH、FDKFH、FNBZFH | 用原匹配字段比较，读取超过 1000 行并到末页 | 无 `-104`；第一页 `FETCH FIRST`，后续页 `ROW_NUMBER()`；无 DB2 `LIMIT` / `OFFSET` |
| LONSTS | 超过 10 万行，分别选择随机、首尾、混合抽样 | 三种策略均执行成功；显示抽样/有限覆盖，不能用于全量同步 |
| DEPSTS | 两端独立计数，再比较 | 计数、读取数量和结果说明一致；真实差异保留，不强行判相同 |

DB2 示例（按实际 schema 替换）：

```sql
SELECT COUNT(*) AS ROW_COUNT FROM "ODS"."DEPSTS";
SELECT COUNT(*) AS ROW_COUNT FROM "ODS"."FCKFH";
SELECT COUNT(*) AS ROW_COUNT FROM "ODS"."LONSTS";
```

TiDB 示例：

```sql
SELECT COUNT(*) AS ROW_COUNT FROM `目标数据库`.`DEPSTS`;
```

原报告的源端 365 行、目标端 19877 行可能是真实数据差异，也可能是连接、schema 或读取问题。
若独立计数确实为 365/19877，不能仅凭数量认定有程序缺陷。
若计数要求读取 19877 行却只读到 365 行，新版本应失败并拒绝生成同步方案。

## CUSTINFO 字符错误定位

1. 在 SQL 编辑器对该表先只读匹配字段，再按列逐步加入字符列，缩小失败列。
2. 若转换在读取列值时失败，可见错误文字附带列序号、可取得的列名、JDBC 类型和异常类链；结构化详情同时保留 `conversion.columnIndex`、`columnName`、`jdbcType` 和有界 `causeClasses`。某些错误发生在执行或 `next()` 阶段，无法可靠得出列名，此时只返回已知信息。
3. 保留原 `vendorCode=-4220`、SQLSTATE 和异常类型；`MalformedInputException` / `UnmappableCharacterException` 还包含 `inputLength`。诊断不会收集业务行内容。
4. 按匹配键范围缩小失败行，再查询字符列的 HEX。以下是模板，按真实列类型和键值替换；数字键不要加字符引号：

```sql
SELECT "ACCT_NO", HEX("问题字符列") AS VALUE_HEX
FROM "ODS"."CUSTINFO"
WHERE "ACCT_NO" >= '范围开始'
  AND "ACCT_NO" < '范围结束'
ORDER BY "ACCT_NO"
FETCH FIRST 100 ROWS ONLY;
```

HEX 返回 ASCII 表示的字节，有助于区分列声明与实际存储。对于 LOB，先从小范围、受限长度的读取开始，避免大字段全量传输。
比较不会将正常 JDBC 字符串重新按 GB18030 解码，也不会将错误字节猜测为另一种编码。
只有两端合法文本（包括已存在的 GB18030 四字节字符）能正确读取，才算字符比较通过。
对于非法数据，严格失败并能定位原因算错误处理通过，不等于该表的数据问题已经修复。

## 反馈清单与边界

- 构建清单、安装包 SHA256、DB2/JCC/JVM/TiDB 版本。
- 源端数据库代码页、问题列类型及代码页、目标表 DDL 和连接字符集。
- 六张表的独立计数、比较方式、读取数量和完整错误详情；必要时提供脱敏 HEX 样本。
- 验证只使用查询和比较，不勾选执行同步。不要提供数据库密码。

尚无内网反馈时，验收记录必须标注“真实数据库待验证”。
